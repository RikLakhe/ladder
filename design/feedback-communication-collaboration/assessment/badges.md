# Feedback, Communication & Collaboration — Badge Catalog

**Status:** active — badge system layered on top of the redesigned Phase D assessment instruments (rubrics, demo/structured-conversation checklists, portfolio requirements) in this folder, and on `00-evidence-bundle-standard.md`.
**Scope:** Part 1 below is copied verbatim, structure-for-structure, from `competencies/technical-skill/assessment/badges.md` Part 1 — the generic, reusable badge pattern. Only Part 2 (names, artifacts, thresholds) and Part 3's competency-specific instantiations are new here. Per that file's §1.4 reuse note, this file does not re-derive the pattern.

Badges do not replace the assessment instruments in `01-work-product-review-rubric.md` (or `02-live-demo-checklist.md` / structured-conversation checklist) and `03-portfolio-requirements.md` in each `pf*/` folder — a badge is *awarded* when a candidate clears the bar those instruments already define, using the bundle standard in `00-evidence-bundle-standard.md`. Badges exist to make "substantial, portfolio-worthy work" legible and portable: a badge is evidence a specific piece of real work cleared a specific bar, not a record of attendance, training completion, or a quiz score.

**Back-port note (2026-08-03):** Leadership's six-persona review surfaced a further generic, competency-agnostic refinement: the co-signer / §1.8 evidence-source collapse clause now appended to §1.6a below — for a genuinely permanently-siloed account, the same delivery/account manager is often both the §1.8 evidence source and the required Tier 5/6 co-signer, collapsing two supposedly independent checks into one; where this collapse would otherwise occur, the technical verifier must independently interview the cited client contact directly before the badge is awarded. Ported into this file below.

## Part 1 — The Reusable Badge Pattern (structural, competency-agnostic)

Copied verbatim from Technical Skill's `badges.md` (canonical pattern source). Do not modify this section's structure when reusing it elsewhere — only Part 2/3 content is competency-specific.

### 1.1 Badge object — required fields

Every badge, in every competency, is defined by these seven fields. No badge is complete without all seven.

| Field | Definition |
|---|---|
| **Badge ID** | `<CompetencyCode>-<PF#>-<Level>` — e.g. `FCC-1-P4`. Stable, referenced from IDPs and assessment files. Never reused for a different achievement even if a badge is retired. |
| **Name** | A short, specific, memorable label for the achievement (not the competency name restated). |
| **Certifies** | One sentence, in the same verb+object+qualifier grammar as the standard's PCs: the specific, real-world capability claim an employer/reviewer/client could rely on if this badge is on someone's record. |
| **Evidence required** | The exact artifact or artifact bundle a candidate must produce — named specifically enough that two different assessors would collect the same thing. Always points back to a named row/item in this PF's rubric, checklist, or portfolio requirements (never a new, uncosted requirement invented only for the badge). Where the badge's Certifies line depends on an adoption/spread claim, the artifact named here is the adoption-evidence record defined in §1.6, not a description of adoption. Where the badge sits at Tier 5 (P6) or Tier 6 (P7), the field may name a services-specific alternate evidence option per §1.8, alongside (never instead of) the internal-standards evidence. Where a badge's required evidence type is vulnerable to being cut short by a mid-rotation client change (a bundle, a continuity-dependent cycle record, or a cross-account claim), the field should cross-reference §1.7 (assignment-limited status) as the fallback, rather than leaving that gap to be discovered ad hoc at review time. |
| **Completion bar** | The rubric/checklist/portfolio threshold that must be met — stated as "meets [row] at [level] with no HIGH/RED gaps," not a vague quality adjective. |
| **Verifier** | Who is authorized to sign off (role/level, never "self-certified"). Matches the "who can assess" line in the underlying instrument. For badges tied to a specific client/account work engagement at Tier 3 (P4) and Tier 5 (P6) — where a misrepresented work context is both plausible and hard for a purely technical reviewer to catch — the named technical verifier is joined by a **co-signer**: the engineer's direct delivery/account manager, who confirms the claimed work context and scope actually happened. The technical verifier certifies the competency; the co-signer certifies the story is real. See §1.6a for the specific case where the co-signer and a §1.8 evidence source would otherwise be the same person. |
| **Tier** | Which of the six generic tiers (§1.2) the badge belongs to — set by the level it's tied to, not by how the competency's PF happens to be named. |

### 1.2 Generic tiers (map 1:1 to LFT's P2–P7 scope column, reusable across competencies)

| Tier | Maps to ladder level(s) | What the tier certifies, generically |
|---|---|---|
| **Tier 1 — Foundation** | P2 | Executes a well-defined unit of work correctly, with guidance, within a single task. |
| **Tier 2 — Practitioner** | P3 | Executes the same class of work unaided, within the scope of an epic. |
| **Tier 3 — Senior Practitioner** | P4 | Executes more complex/ambiguous work unaided, within team scope, to a production-ready bar. |
| **Tier 4 — Guide** | P5 | Facilitates, mentors, or drives a change at team scope, working with the team's stakeholders. |
| **Tier 5 — Multiplier** | P6 | Facilitates or converges practice across several teams. |
| **Tier 6 — Steward** | P7 | Sets and governs standards/strategy at organizational scope. |

(Not every competency's every PF will produce a badge at every tier — a PF that caps at P4 stops at Tier 3. Don't force higher tiers to fill out a table; see the methodology's level-scoping principle. This competency's three PFs all run the full P2–P7 ladder per `functional-analysis.md`, so all six tiers are used in every PF below.)

### 1.3 Badge award rule (generic)

A badge is awarded when, and only when:
1. The named evidence artifact/bundle exists and is reviewable (not described secondhand) — or, where §1.5's alternate evidence path applies, an in-place attestation exists in its place.
2. The completion bar (the rubric/checklist/portfolio threshold) is met with **no HIGH/RED-severity gap** on any criterion the badge's "Certifies" line depends on.
3. A verifier at the required role/level signs off, in writing, with the artifact link and sign-off date recorded — including the delivery/account-manager co-signer at Tier 3/Tier 5, where §1.1 requires one, and including the independent-interview step at §1.6a where the co-signer/§1.8-source collapse applies.
4. The evidence reflects **real work product**, not a constructed showcase exercise built solely to earn the badge — per the "substantial, portfolio-worthy work" design principle, badges attach to actual feedback exchanges/1:1 notes/PR comments/documentation/client correspondence/on-call records/retro notes, never to a standalone quiz, a training completion, or a simulated exercise with no real stakes. (Live-demo/structured-conversation-anchored badges are the one exception structurally allowed to use a scenario rather than found-in-the-wild work, because the standard itself specifies that assessment mode at that level — but even there, the scenario is cross-checked against the candidate's real evidence bundle per `00-evidence-bundle-standard.md`, not a standalone performance.)

### 1.5 Evidence-extraction constraints (generic)

Real work evidence sometimes cannot leave a client's contracted environment (NDA, data residency, contractual IP terms). This is a constraint on the *channel* evidence travels through, not a reason to waive the bar, and not something the engineer should have to solve alone:

- **Default path:** redact/sanitize the artifact (client-identifying names, data, proprietary logic) before it leaves the client environment, per the engagement's data-handling policy.
- **Expediting sign-off is the sponsoring delivery lead/account manager's job, not the engineer's to chase alone.** They own getting redaction/export sign-off actioned promptly — a stalled sign-off is a delivery-lead follow-up item, not a badge blocker the engineer is expected to resolve solo.
- **Alternate evidence path — when redaction/export is contractually impossible for a required PF:** the verifier reviews the artifact *in place*, inside the client's own environment/tooling (screen share, on-site review, client-hosted access), and signs a written attestation recording what was reviewed, when, and against which rubric/checklist row. No diff, document, or data needs to leave the client system. The attestation substitutes for the exported artifact; it does not lower the completion bar.
- This path applies to any competency's badge, not just Technical Skill — reuse it as-is. In this competency it applies most often to client status emails, escalation threads, and client-side feedback records that live entirely inside a client's own email/ticketing system.

### 1.5a Access-loss is distinct from confidentiality (generic)

§1.5 above addresses evidence that *exists but can't leave* the client's environment. A different, and more common, failure mode — especially at P3 — is that the engineer rotates off a client **before** the evidence could be extracted or reviewed in place at all: access to the outgoing client's systems, Slack, or ticketing tool is simply revoked as part of offboarding, with no confidentiality issue in play.

- This is an **access-loss** case, not a confidentiality case: there is no NDA/IP barrier being worked around, the evidence is just physically gone.
- Do not require the §1.5 in-place-attestation path here — the verifier can no longer review anything in place, because access no longer exists.
- Treat this via **§1.7 (assignment-limited status)** instead: the badge is marked "blocked — assignment-limited," not "not earned" and not "failed," and the manager/theme owner works a resolution per §1.7's terms.

### 1.6 Instrumenting "adoption" claims (generic)

Any completion bar or Certifies line that uses adoption/spread language ("adopted by other teams," "sustained use," "adopted by ≥N teams/accounts/stakeholders") must be backed by a concrete adoption-evidence artifact, not asserted from memory or a candidate's own account. The generic artifact is a 3-part record:
1. A **named contact** at the adopting team/account who can confirm the claim if asked.
2. A **dated reference** to where the adoption is visible (Slack thread, email, PR, ticket, meeting note, retro doc).
3. **One line** describing what concretely changed as a result (a practice actually followed, a habit that spread, a decision that was reversed) — not "they liked it."

A badge whose Certifies line depends on adoption cannot be awarded on the strength of the candidate's own description of adoption alone — this artifact is the required evidence, named explicitly in that badge's "Evidence required" field. In this competency, this applies to nearly every P5–P7 culture-fostering badge (feedback, communication, documentation, and disagreement/collaboration culture rows all use adoption language).

### 1.6a Permanently-siloed roles: §1.8 is the expected path, not the fallback (generic)

§1.6 and §1.7 above are written against a rotation model: a candidate normally gets, or will eventually get, visibility into more than one team/account, and a gap in that visibility is either temporary (§1.7's assignment-limited status) or fillable by producing the §1.6 adoption artifact. That model doesn't fit every P6/P7 case.

Some P6/P7 candidates work a **steady-state, permanently-siloed role**: a single large account with a durable client-imposed wall (security clearance, contractual exclusivity, a dedicated long-term staffing model) that has never given them, and realistically never will give them, shared visibility into a second team/account. This is not a rotation gap waiting to close — it is the stable shape of the role.

- Do **not** default to treating §1.6's cross-team artifact as the primary expectation with §1.8's services-signal path as a fallback for these candidates — that setup structurally penalizes a role LFT itself staffed this way.
- Instead, for a candidate the manager/theme owner determines is genuinely permanently-siloed (not merely mid-rotation), **§1.8's services-signal path is the primary, expected route** to the P6/P7 badge, and the §1.6 cross-team artifact becomes the alternate/supplementary path if it happens to be available — the two paths swap which one is "expected" versus "alternate" for this candidate only.
- This determination (permanently-siloed vs. temporarily-siloed) is made by the manager/theme owner, recorded with the badge sign-off, and revisited if the candidate's staffing model changes.
- This does not lower the bar — the candidate still needs a real, corroborated services-signal artifact per §1.8 (named client contact, dated reference, concrete change), not a description of goodwill.
- **Co-signer / §1.8 evidence-source collapse (added 2026-08-03, generic — back-ported from Leadership's badges.md):** for a genuinely permanently-siloed account, the same delivery/account manager is often both the §1.8 evidence source (the person confirming the client-relationship signal itself) and the Tier 5/6 co-signer §1.1 requires (the person confirming the claimed work context is real). Used together unmodified, this collapses two supposedly independent checks into one single source. Where this collapse would otherwise occur: the technical verifier (the P6+ engineer) must **independently interview the cited client contact directly** — not rely solely on the co-signer's secondhand account of what the client contact said or would say — before the badge is awarded. This is a required verification step, documented at sign-off (who was contacted, when, what was confirmed, by whom), not an optional enhancement and not satisfied by the co-signer's attestation alone.

### 1.7 Assignment-limited badges (generic)

Some required evidence types depend on what an engineer's current client assignment happens to expose them to, not on their skill — no ticket ever involves a business stakeholder; the client bans external client contact for junior staff; the engineer has never been rostered for on-call; a client rotation cuts off a bundle or cycle-continuity requirement mid-way. When a structural assignment constraint prevents producing a required evidence type for more than one review cycle:
- The badge is marked **"blocked — assignment-limited"** in the person's record — distinct from both "not earned" (skill gap) and "failed" (attempted, didn't clear the bar).
- The manager or theme owner tracks this status and works either a reassignment that restores access to the evidence type, or an assignment-appropriate alternate evidence substitute agreed with the theme owner. The default resolution is never "go build a side project to manufacture evidence."
- This status is reviewed at the same cadence as the badge/IDP review, not left open indefinitely.
- **Mid-rotation client swaps specifically:** if a client rotation breaks bundle or cycle continuity before required evidence is complete — the 4–6 week evidence-bundle window the candidate was building against ends early because they were moved to a new account — this is an assignment-limited case, not an unearned badge. Whatever partial record exists is preserved and counted toward the next cycle's evidence rather than discarded.

### 1.8 Services-company impact signal (generic, Tier 5/Tier 6 only)

At Tier 5 (P6) and Tier 6 (P7), pure internal-standards evidence ("adopted by internal teams," "org standard set") is not the only legitimate signal of multiplier/steward-level impact at a services company — impact can also show up in the account/client relationship itself. Where natural for the PF, the badge's "Evidence required" field lists a second, equally valid evidence option, such as: retained/expanded technical credibility on an account, a client citing the candidate's communication/feedback/collaboration practice as a reason for continued or expanded engagement, or external reputation (talks, community standing) that visibly contributed to client trust. This is always an **OR** alternative alongside the internal-standards evidence, never a replacement for it — a candidate can clear the badge via either path. (See §1.6a for the permanently-siloed-role case where this path becomes the *expected* route rather than the alternate.)

## Part 3 — How badges are administered

- **Recording:** badge awards are recorded against the person's file (`people/<name>.md`) and/or IDP (`1-1s/<name>-idp.md`) with Badge ID, date, artifact link, and verifier — never inside this catalog file, which stays a reference, not a per-person ledger.
- **No self-certification:** every badge requires the Verifier role/level named in its row; a candidate cannot award their own badge.
- **Verifier co-signing at Tier 3 (P4) / Tier 5 (P6):** per §1.1, badges at these tiers require both a technical verifier and the candidate's delivery/account manager as co-signer. The technical verifier certifies the behavior demonstrated; the co-signer confirms the claimed work context (which stakeholder, which engagement, which matrixed/multi-engagement situation) actually happened. Both sign-offs, with dates, are recorded. Where the co-signer would also be the §1.8 evidence source (permanently-siloed accounts), see §1.6a's independent-interview requirement.
- **Evidence-extraction and confidentiality (§1.5):** the sponsoring delivery lead/account manager for the engagement — not the engineer alone — is responsible for expediting any redaction/export sign-off a badge's evidence needs (client status emails, escalation threads, client-side feedback records). If a client's contract terms make evidence extraction impossible for a required PF, use the in-place attestation path in §1.5 rather than treating the badge as unearnable.
- **Access-loss vs. confidentiality (§1.5a):** if an engineer rotates off a client and loses system access before evidence could be extracted or reviewed in place at all — with no confidentiality issue involved, just offboarding — this is an access-loss case, not a §1.5 confidentiality case. Route it through §1.7 (assignment-limited) instead of requiring an in-place review that's no longer physically possible.
- **Assignment-limited badges (§1.7):** a badge blocked by the engineer's current assignment (no matrixed engagement, no client contact, never rostered for on-call, single-staffed with no multi-engagement exposure, no coachable teammate, or a mid-rotation client swap that cut a bundle short) for more than one review cycle is recorded as **"blocked — assignment-limited"** — distinct from both "not earned" and "failed." The manager/theme owner tracks reassignment or an agreed alternate evidence substitute at the same review cadence as the badge/IDP itself. **Cross-referenced from:** FCC-1-P4, FCC-1-P6, FCC-2-P2, FCC-2-P3, FCC-2-P6, FCC-3-P2, FCC-3-P3, FCC-3-P4, FCC-3-P5, FCC-3-P6 above — all bundle- or continuity-dependent badges vulnerable to client rotation or assignment gaps.
- **Permanently-siloed roles (§1.6a):** for a P6/P7 candidate the manager/theme owner determines is genuinely permanently siloed on a single account (not mid-rotation), the §1.8 services-signal path is the expected route to the badge, not a fallback behind §1.6's cross-team artifact — see §1.6a for the full test and recording requirement, including the independent-interview step where the co-signer and the §1.8 evidence source would otherwise be the same person.
- **Protected time:** time spent assembling the 4–6 week evidence bundle (`00-evidence-bundle-standard.md`) required at P2–P4, or preparing for a live-demo/structured-conversation badge session, is expected to be accounted for as part of normal professional development time — not unpaid overtime, and not something to negotiate against billable hours unilaterally. The same protection extends to time spent identifying and packaging portfolio evidence for P5+ review (finding dated artifacts, getting a named third party to confirm a claim in writing per §1.6, assembling the submission format each PF's `03-portfolio-requirements.md` requires). Schedule this by coordinating with the engineer's delivery/account lead, not by sacrificing client deliverables.
- **Adoption claims (§1.6):** any badge whose completion bar or Certifies line depends on adoption/spread language requires the 3-part adoption-evidence artifact (named contact, dated reference, what changed) — this applies to nearly every P5–P7 badge in Part 2 above, since all three PFs' culture-fostering rows use adoption language from P5 up.
- **Services-specific signal at Tier 5/6 (§1.8):** where listed in Part 2, the services-specific alternative (a client citing the candidate's practice as a reason for continued/expanded engagement, or external reputation contributing to client trust) is always an OR alongside the internal-standards evidence, never a substitute requirement layered on top — except for the permanently-siloed case in §1.6a, where it becomes the expected route.
- **No retroactive downgrade requirement:** badges are not re-litigated when the underlying standard is revised — a badge earned under a prior standard version remains valid unless the theme lead flags a material gap.
- **Relationship to promotion:** badges are evidence *inputs* to a promotion/GAP decision, not a substitute for it — a P5+ promotion still requires the full portfolio review in each PF's `03-portfolio-requirements.md`; the badges for that level are a fast way to confirm the underlying bars were already cleared.
- **Relationship to training:** completing training materials in `training/` (if/when built for this competency) does not itself earn a badge — badges attach only to assessed, real work product per §1.3 above.
